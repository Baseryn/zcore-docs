In Part 1 ([The Repository Pattern in FastAPI](/blog/repository-pattern-fastapi)), we explored how to draw clean data boundaries with SQLAlchemy 2.0 without fighting the ORM. 

Once your repositories are in place, standard architectural advice immediately points to the next step: **introduce a Service layer.**

A common architectural recommendation is:
> *"Keep your route handlers thin! Routes should only handle HTTP status codes and serialization. All business logic belongs in the Service layer."*

It sounds disciplined. But after a few weeks of building standard application modules, many developers look at their service files and experience a familiar frustration:

```python
# The "Pass-Through" (Forwarding) Service
class ProductService:
    def __init__(self, repository: ProductRepository):
        self.repository = repository

    async def get(self, id: UUID) -> Product:
        return await self.repository.get(id=id)

    async def list(self, pagination: Any) -> list[Product]:
        return await self.repository.get_list(pagination=pagination)

    async def delete(self, id: UUID) -> None:
        await self.repository.delete(target=id)
```

In many routine CRUD operations, the service function does little more than forward arguments directly to the repository.

You are maintaining three separate files (Router, Service, Repository) to execute a single read or delete operation. 

This is the **Pass-Through Service Trap** (or Forwarding Service). In this post, we’ll analyze why this happens, why simply deleting the service layer creates worse problems, and how we solved this using **Lifecycle Hooks** and safe transaction awareness.

---

## 1. The Pendulum Swing: Why Deleting the Service Layer Backfires

When developers get exhausted by writing pass-through forwarders, they often swing to the opposite extreme: **they delete the service layer entirely.**

They call repositories (or raw queries) directly inside the FastAPI route handler:

```python
@router.post("/orders")
async def create_order(
    payload: OrderCreate,
    repo: OrderRepository = Depends(),
    db: AsyncSession = Depends(get_db),
):
    # Route handler now owns business logic:
    order = await repo.create(payload)
    await audit_logger.record(order.id)
    await db.commit()
    return order
```

This feels fast at first. But the moment real business requirements arrive, this approach collapses:
1. **Hidden Side Effects:** If an order requires deducting inventory, computing discounts, and dispatching events, your route handler quickly balloons to 150 lines of mixed concerns.
2. **Coupled Testing:** Testing the workflow becomes tightly coupled to HTTP handling and dependency wiring, rather than exercising a reusable application service directly.
3. **Loss of Reusability:** If an asynchronous background worker, a CLI task, or an internal event subscriber needs to create an order, it cannot invoke the route handler. You are forced to copy-paste the logic or refactor back into a service under deadline pressure.

We don't want fat route handlers. But we also don't want anemic forwarders.

---

## 2. The Core Problem: Re-inventing the CRUD Lifecycle

The root cause of the Pass-Through trap is that developers treat every single domain service as a bespoke, hand-crafted pipeline—even when the underlying lifecycle is identical:

```text
Validated Payload → Pre-persistence Mutation & Domain Checks → Persistence → Post-processing → Transaction Finalization
```

Whether you are creating a `User`, a `Company`, or a `Product`, this sequence rarely changes. What changes are the **specific domain rules** (e.g., hashing a password before creating a user, or attaching dynamic tenant metadata).

Instead of forcing developers to write boilerplate forwarders over and over, a mature service layer should implement the **Template Method Pattern**: provide the end-to-end orchestration flow out of the box, and expose granular **Lifecycle Hooks** for domain-specific logic.

---

## 3. The Implementation: Orchestration with Composable Hooks

In our architecture, we divided the business layer into focused capabilities matching the repository: `ReadServiceMixin`, `WriteServiceMixin`, and `SearchServiceMixin`.

The following is a simplified excerpt of the write-service implementation. The surrounding module defines `AbstractService`; unrelated imports and methods are omitted for clarity:

```python
from typing import Any, Generic, TypeVar

from pydantic import BaseModel
from zcore.db.setup import Base

ModelType = TypeVar("ModelType", bound=Base)

class WriteServiceMixin(Generic[ModelType], AbstractService[ModelType]):
    """Standardized mutation, persistence, and deletion orchestration."""

    async def pre_create(self, schema: BaseModel) -> dict[str, Any] | None:
        """Triggered prior to database insertion. Return trusted fields to merge."""
        return None

    async def post_create(self, model: ModelType) -> None:
        """Triggered after insertion, before commit (in-session post-processing)."""
        pass

    async def pre_update(
        self, target: ModelType | Any, schema: BaseModel, partial: bool
    ) -> dict[str, Any] | None:
        return None

    async def post_update(self, model: ModelType) -> None:
        pass

    async def pre_delete(self, id: Any, force: bool = False) -> None:
        pass

    async def post_delete(self, model: ModelType, force: bool = False) -> None:
        pass
```

### The Orchestrator Method
The `create` method orchestrates the entire pipeline. Developers never have to rewrite this boilerplate:

```python
    async def create(self, schema: BaseModel, **extra_data: Any) -> ModelType:
        # Step A: Run domain pre-flight logic; explicit extra_data overrides hook data
        hook_data = await self.pre_create(schema) or {}
        combined_extra = {**hook_data, **extra_data}

        # Step B: Execute persistence via repository (issues INSERT and flush)
        result = await self.on_create(schema, **combined_extra)

        # Step C: Run in-session post-processing
        await self.post_create(result)

        # Step D: Safely finalize the transaction
        await self._safe_commit()
        return result
```

Notice two critical architectural traits here:
- **Protocol-Agnostic Design:** The service raises application-level, framework-neutral exceptions (such as `EntityNotFound`) instead of Starlette's `HTTPException`. The HTTP layer handles translation at the API boundary, keeping the service completely independent of web protocols.
- **Hook-driven Extension:** For standard CRUD behavior, a service can require only minimal boilerplate to bind the model and repository. When an entity needs business rules, you can override the relevant lifecycle hook without rewriting the persistence pipeline.

---

## 4. Understanding Hook Timing: In-Session vs. Post-Commit

A critical architectural distinction that developers must understand when using lifecycle hooks is the timing of `post_create`:

```text
[on_create (flush)] ──→ [post_create (in-session)] ──→ [_safe_commit (commit)]
```

`post_create` is an **in-session hook (Post-Insert, Pre-Commit)**:
- **What it is for:** Inspecting auto-generated primary keys or timestamps, updating sibling entities within the same database transaction, or staging deferred events.
- **What it is NOT for:** Irreversible external network calls (such as directly invoking a third-party payment gateway or sending an SMS).

If you fire an external network call directly inside `post_create` and the subsequent `_safe_commit()` fails due to a database constraint or serialization conflict, your external side-effect has already occurred while your database rolled back—causing a **phantom side-effect**.

For external side-effects:
- **In-memory event queues:** Suitable for transient, best-effort notifications where losing an event during an abrupt process termination is acceptable.
- **Transactional Outbox Table:** Essential for mission-critical operations. Storing the event row in an outbox table within the *same* atomic database transaction guarantees **event durability** (eliminating dual-write inconsistencies). However, note the distinction: persisting the event atomically only guarantees it is *safely stored*; **guaranteed delivery** still requires an asynchronous outbox relay worker, retry policies, and idempotent consumers to handle eventual dispatch.

## 5. Real-World Example: Domain Logic Without the Boilerplate

Look at how concise a domain service becomes when you only write the code unique to your business rules:

```python
# 1. The Schema (schemas.py)
class UserCreate(BaseModel):
    email: EmailStr
    # Validated on HTTP input, but excluded during model_dump()
    password: str = Field(min_length=8, max_length=128, exclude=True)


# 2. The Service (services.py)
class UserService(BaseService[User]):
    def __init__(self, repository: UserRepository):
        super().__init__(model=User, repository=repository)

    async def pre_create(self, schema: UserCreate) -> dict[str, Any]:
        # Hash password and inject into extra_data
        hashed = Security.hash_password(schema.password)
        return {
            "hashed_password": hashed,
            "tenant_id": ctx.get("tenant_id"),
        }

    async def post_create(self, user: User) -> None:
        # Update user activity log in the same atomic session
        await self.repository.log_audit_event(user.id, action="user_registered")
```

Because `password` is marked with `exclude=True`, Pydantic validates it on the incoming request, but omits it when dumping into the repository. The hook cleanly intercepts the raw value, generates the hash, and injects it directly into the database payload.

All standard persistence calls, dialect-aware queries, error handling, and transaction finalization remain entirely encapsulated. (And with constructor auto-wiring, you don't have to write manual dependency injection factories to instantiate it).

## 6. The Transaction Dilemma: The `_safe_commit` Pattern

One of the thorniest architectural questions in a layered FastAPI system is: **Who owns the transaction commit?**

- If the service **always** commits, it cannot be safely composed. If an `OrderService` needs to coordinate with an `InventoryService.deduct()` and a `LedgerService.record_entry()`, the inner service calls will commit prematurely, destroying transaction atomicity across those database tables if a subsequent step fails.
- If the service **never** commits, developers must remember to manually commit in every single endpoint, re-introducing boilerplate.

We solved this through conditional transaction awareness (`_safe_commit`):

```python
    async def _safe_commit(self) -> None:
        """Execute a session commit only if transaction state is not managed externally."""
        session_info = self.repository.db.info
        if not session_info.get("uow_managed", False):
            try:
                await self.repository.db.commit()
            except Exception:
                await self.repository.db.rollback()
                raise
```

### How the Rollback Guarantee Operates:
1. **Standalone Execution:** When an endpoint calls `user_service.create()` directly, `uow_managed` is `False`. The service cleanly commits the transaction upon completion. If an exception occurs during `pre_create`, `on_create`, or `post_create`, it propagates outward to the surrounding transaction or request-session scope, which is responsible for executing the rollback.
2. **Coordinated Workflows:** When multiple services participate in a higher-level transaction, an explicit **Unit of Work** marks `uow_managed = True`. The service respects this boundary: it flushes queries so generated IDs are available to sibling services, but skips the physical commit—leaving the atomic commit or rollback decision entirely to the outer Unit of Work boundary.

### The Cooperative Contract (and Its Boundaries)
It is important to understand the mechanics and limits of this check: `session.info` is SQLAlchemy's mutable dictionary scoped to a single `AsyncSession` instance. 

`_safe_commit()` operates on an **in-process, cooperative contract**:
- **Shared Session Requirement:** All participating services must receive the same `AsyncSession` instance. In the standard request-scoped setup, resolving them within the same scope provides that shared instance. Services instantiated manually or resolved through separate scopes may receive different sessions and therefore will not share the same transaction boundary.
- **Cooperative Opt-In:** It is not an engine-level distributed transaction coordinator. If a developer coordinates multiple mutating services without wrapping them in an outer Unit of Work context (or without explicitly setting `uow_managed = True`), each service assumes standalone ownership and will commit independently.

This contract trades heavy, rigid transaction management for a pragmatic convention that keeps individual CRUD operations self-contained while allowing multi-service workflows to remain atomic when coordinated.

---

## 7. What This Pattern Does NOT Try to Do

To keep architecture clean and prevent excessive inheritance hierarchies, we establish strict non-goals:

1. **It does not force every workflow into hooks:** If an endpoint executes a complex read-only report aggregating data from external APIs without database mutations, you don't force it into `pre_create`. Write an explicit, named service method (`generate_monthly_report()`).
2. **It does not replace domain models:** Business validation and state transition rules that enforce invariants belong in your Domain Model—not necessarily every SQLAlchemy ORM model that exists primarily for table mapping and persistence. The service layer acts as the **application orchestrator**, coordinating persistence, hooks, and transaction boundaries.

---

## 8. Summary: Stop Writing Forwarders

A Service layer in FastAPI should not be an anemic proxy that merely mirrors repository methods. 

By utilizing reusable base services equipped with standard CRUD lifecycles and explicit hooks (`pre_create`, `post_create`, `_safe_commit`), you eliminate hundreds of lines of useless boilerplate while ensuring that your business rules and transaction boundaries remain clean, testable, and safe.
